## 1. 我们做了什么（概述）

数据库是整个系统的"记忆"，负责记录所有仿真数据。具体来说：

- **存储仿真实例信息**：每次启动仿真时，记录用了什么参数、什么时间开始
- **存储每秒快照数据**：仿真运行时，每秒把各窗口人数、桌子使用情况存下来
- **提供数据查询**：仿真结束后，后端从数据库取出历史数据生成趋势图和评价
- **自动清理旧数据**：定期删除超过 7 天的旧记录，防止数据库文件无限变大

数据库文件是项目根目录下的 `database.db`，第一次运行程序时自动创建。

---

## 2. 数据库用到了哪些技术

| 技术 | 版本 | 作用 |
|------|------|------|
| **SQLite** | Python 内置 (`sqlite3` 模块) | 数据库引擎 |
| **WAL 模式** | SQLite 3.7+ | 并发控制，支持一写多读 |
| **SQL** | 标准 SQL | 建表、插数据、查数据 |

**没有用 ORM**（如 SQLAlchemy），而是直接用原生 SQL 语句。这样更直观，也避免了 ORM 的学习成本。

---

## 3. 为什么选 SQLite

在 MySQL、PostgreSQL、SQLite 三者中我们选了 SQLite：

| 维度 | SQLite | MySQL / PostgreSQL |
|------|--------|-------------------|
| **部署** | 零配置，一个文件就是数据库 | 需要安装服务端、配置用户 |
| **迁移** | 拷贝 `.db` 文件即可 | 需要 dump + restore |
| **并发** | 支持有限（适合小规模） | 支持高并发 |
| **维护** | 无需运维 | 需要管理服务进程 |
| **性能** | 数据量小时很快 | 数据量大时更优 |

### 选 SQLite 的理由

1. **项目规模小**：这是教学/演示项目，不是要支撑成千上万用户的生产系统
2. **零配置**：不需要安装数据库服务器，评审老师直接跑 `python app.py` 就能运行
3. **数据量可预期**：每秒一条记录，一次仿真 30 分钟才 1800 条，SQLite 轻松应对
4. **易于备份**：数据库就是一个文件，拷贝 `database.db` 就完成了备份

### SQLite 的局限（我们怎么应对）

- **并发写入能力弱** → 启用 WAL 模式 + 设置锁超时
- **不支持网络访问** → 我们本身就是单机应用，不需要
- **数据类型弱** → 用代码层校验保证数据正确性

## 4. 数据库表是怎么设计的

### 4.1 仿真信息表 `simulation_info`

```sql
CREATE TABLE simulation_info (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,  -- 自增主键
    session_id   TEXT NOT NULL UNIQUE,               -- 会话 ID（前端生成）
    dining_time  INTEGER NOT NULL,                    -- 用餐时间（分钟）
    meal_time    INTEGER NOT NULL,                    -- 打饭时间（秒/人）
    max_people   INTEGER NOT NULL,                    -- 每分钟最大进入人数
    window_num   INTEGER NOT NULL,                    -- 窗口数量
    table_num    INTEGER NOT NULL,                    -- 桌子数量
    start_time   TEXT NOT NULL,                       -- 仿真开始时间
    end_time     TEXT,                                -- 仿真结束时间（NULL=未结束）
    status       INTEGER NOT NULL DEFAULT 0           -- 0=运行中, 1=已结束
);
```

**字段说明**：

| 字段 | 类型 | 为什么这样设计 |
|------|------|----------------|
| `id` | INTEGER 自增 | 主键，唯一标识一条记录 |
| `session_id` | TEXT UNIQUE | 前端生成的 UUID，用于关联前后端。加 UNIQUE 防止重复 |
| `dining_time` 等 | INTEGER | 参数全是整数，不需要小数 |
| `start_time` | TEXT | SQLite 没有 DATETIME 类型，存文本格式 `2026-06-14 15:30:00` |
| `end_time` | TEXT, 可NULL | 运行中时为空，结束后写入时间 |
| `status` | INTEGER, 默认0 | 用 0/1 而不是字符串，查询效率更高 |

### 4.2 仿真数据表 `simulation_data`

```sql
CREATE TABLE simulation_data (
    id              INTEGER PRIMARY KEY AUTOINCREMENT, -- 自增主键
    simulation_id   INTEGER NOT NULL,                  -- 外键 → simulation_info.id
    time_step       INTEGER NOT NULL,                  -- 第几秒
    window_people   TEXT NOT NULL,                     -- 各窗口人数（逗号分隔）
    used_table      INTEGER NOT NULL,                  -- 已用桌子数
    remaining_table INTEGER NOT NULL,                  -- 剩余桌子数
    create_time     TEXT NOT NULL,                     -- 写入时间
    FOREIGN KEY (simulation_id) REFERENCES simulation_info(id)
);
```

**字段说明**：

| 字段 | 类型 | 为什么这样设计 |
|------|------|----------------|
| `simulation_id` | INTEGER, 外键 | 关联到哪次仿真。每次仿真有唯一 ID |
| `time_step` | INTEGER | 仿真运行到第几秒。比如 time_step=60 表示第 1 分钟 |
| `window_people` | TEXT | 各窗口排队人数，如 `"3,2,5,1"` 表示 4 个窗口分别有 3、2、5、1 人。**为什么不用数组？** SQLite 不支持数组类型，所以用逗号分隔的字符串存储，读取时再 `split(",")` 还原 |
| `used_table` | INTEGER | 当前已占用的桌子数 |
| `remaining_table` | INTEGER | 当前空闲桌子数 |

### 4.3 表关系

```
simulation_info (1) ──── (N) simulation_data
    id  ←────────────────── simulation_id (外键)
```

一次仿真（`simulation_info` 中的一条记录）对应多条数据快照（`simulation_data` 中的 N 条记录）。

## 5. 数据库代码是怎么组织的

所有数据库相关代码在一个文件 `database.py` 中，定义了一个 `SimulationDatabase` 类。在文件末尾创建**全局单例**：

```python
db = SimulationDatabase()
```

其他模块（`app.py`、`simulation.py`）通过 `from database import db` 拿到这个单例，共享同一个数据库连接。

### 类方法清单

```
SimulationDatabase
    │
    ├─ 初始化
    │   ├─ __init__()         → 连接数据库 + 建表
    │   ├─ _connect()          → sqlite3.connect()
    │   └─ _create_tables()    → CREATE TABLE IF NOT EXISTS
    │
    ├─ simulation_info 表操作
    │   ├─ add_simulation()           INSERT 新仿真
    │   ├─ get_current_simulation()   查 status=0 的仿真
    │   ├─ get_simulation_info_by_session()  按 session_id 查（不限 status）
    │   ├─ get_simulation_info_by_id()       按 id 查
    │   └─ end_simulation()           UPDATE status=1, end_time=now
    │
    ├─ simulation_data 表操作
    │   ├─ add_simulation_data()      INSERT 一条快照
    │   └─ get_simulation_data()      查某次仿真的所有快照
    │
    ├─ 维护
    │   ├─ cleanup_old_data()         删除 7 天前的数据
    │   └─ close()                    关闭连接
    │
    └─ 实例：db（全局单例）
```

### 单例模式的好处

- 整个应用只有一个数据库连接，避免连接数过多
- 所有模块共享同一连接，数据一致性好
- 不需要传参，`from database import db` 直接用

## 6. CRUD 操作详解（增删改查）

### 6.1 增加仿真（add_simulation）

后端启动仿真线程前，先调用这个方法在数据库里"挂号"：

```python
simulation_id = db.add_simulation(
    session_id="abc-123",
    dining_time=20,
    meal_time=5,
    max_people=300,
    window_num=4,
    table_num=100,
)
```

**注意**：插入前会**先删除**该 session 下旧的运行中记录。为什么？如果前端在同一个 session 下重复启动仿真，老记录不能留着影响后续查询。

### 6.2 插入仿真数据（add_simulation_data）

仿真线程每秒调一次：

```python
db.add_simulation_data(
    simulation_id=1,
    time_step=1,
    window_people=[3, 2, 5, 1],  # 列表自动转成 "3,2,5,1"
    used_table=20,
    remaining_table=80,
)
```

`window_people` 是 Python 列表，用 `",".join(map(str, window_people))` 转成逗号分隔字符串存入。

### 6.3 查询运行中的仿真（get_current_simulation）

```sql
SELECT id, dining_time, meal_time, max_people, window_num, table_num
FROM simulation_info
WHERE session_id = ? AND status = 0
```

只查 `status = 0`（运行中）。如果仿真已结束，这里返回 `None`。

### 6.4 查询仿真数据（get_simulation_data）

```sql
SELECT time_step, window_people, used_table, remaining_table
FROM simulation_data
WHERE simulation_id = ?
ORDER BY time_step ASC
```

按时间步升序排列，还原趋势。读取时把 `"3,2,5,1"` 用 `split(",") + map(int)` 还原成列表。

### 6.5 结束仿真（end_simulation）

```sql
UPDATE simulation_info
SET end_time = ?, status = 1
WHERE id = ?
```

把 `status` 从 0 改为 1，写入结束时间。

### 6.6 清理旧数据（cleanup_old_data）

删除 7 天前的已完成仿真及其关联数据。**概率性触发**（约 10% 概率），避免每次启动都扫全表。

## 7. 多线程并发怎么处理

### 7.1 并发场景

```
Flask 主线程                    仿真线程（可能有多个）
    │                               │
    ├─ 读取 simulation_info         ├─ 写入 simulation_data（每秒）
    ├─ 读取 simulation_data         ├─ 写入 simulation_info
    └─ 更新 simulation_info         └─ ...
```

### 7.2 SQLite 的并发限制

SQLite 有三种锁状态：无锁 → 共享锁（读） → 预留锁 → 排他锁（写）。

- **多个线程可以同时读**（共享锁）
- **写操作需要排他锁**（只能一个线程写）
- **默认模式下读写互斥**

### 7.3 我们的解决方案

```python
# database.py — 连接配置
self.conn = sqlite3.connect(
    DB_PATH,
    check_same_thread=False,  # ← 允许跨线程使用连接
    timeout=30,               # ← 等待锁超时 30 秒（默认仅 5 秒）
)
# 启动时启用 WAL 模式
self.conn.execute('PRAGMA journal_mode=WAL')
```

| 配置 | 值 | 作用 |
|------|-----|------|
| `check_same_thread=False` | - | 允许不同线程共用同一个连接对象 |
| `timeout=30` | 30秒 | 获取不到锁时等待多久，而不是立即报错 |
| `journal_mode=WAL` | - | 启用 WAL 模式（见下节） |

## 8. WAL 模式是什么

### 8.1 默认模式 vs WAL 模式

**默认模式（DELETE）**：
```
写操作 → 锁住整个数据库 → 写入 → 解锁
读操作 → 等待写操作完成 → 读取 → 返回
```
**读写互相阻塞！**

**WAL 模式（Write-Ahead Logging，预写日志）**：
```
写操作 → 写入 WAL 文件（.db-wal）→ 不阻塞读
读操作 → 读取原始数据 + WAL 中已提交的更改 → 不阻塞写
```
**读写可以同时进行！**

### 8.2 WAL 模式带来的文件

启用 WAL 后，数据库目录会出现两个额外文件：

| 文件 | 作用 |
|------|------|
| `database.db` | 主数据库文件 |
| `database.db-wal` | 预写日志（Write-Ahead Log） |
| `database.db-shm` | 共享内存索引（Shared Memory） |

这是正常的，不需要手动管理。

### 8.3 为什么 WAL 模式适合我们

- 仿真线程每秒**写一次**数据
- API 请求可能**同时读**数据
- WAL 让读写不互相等待，避免 `database is locked` 错误

## 9. 数据清理策略

### 9.1 为什么需要清理

仿真每秒写入一条记录。如果：
- 每次仿真 30 分钟 = 1800 条
- 每天 50 次仿真 = 90,000 条
- 一个月 = 2,700,000 条

不清理的话数据库文件会越来越大，查询越来越慢。

### 9.2 清理策略

```python
def cleanup_old_data(self, retention_days=7):
    # 1. 概率性触发（约 10% 概率）
    if random.random() > 0.1:
        return
    
    # 2. 删除 simulation_data 表中 7 天前的数据
    DELETE FROM simulation_data
    WHERE simulation_id IN (
        SELECT id FROM simulation_info
        WHERE status = 1
        AND datetime(end_time) < datetime('now', '-7 days')
    )
    
    # 3. 删除 simulation_info 表中 7 天前的记录
    DELETE FROM simulation_info
    WHERE status = 1
    AND datetime(end_time) < datetime('now', '-7 days')
```

**注意三点**：
1. 只删 `status = 1`（已结束）的仿真，不删运行中的
2. 先删子表（`simulation_data`）再删主表（`simulation_info`），保持引用完整性
3. 概率性触发（~10%），避免每次启动都全表扫描

## 10. 数据库怎么和后端对接

### 10.1 启动流程中的数据库操作

```
app.py                           database.py
  │                                  │
  │─ from database import db ──────→  创建连接 + 建表 + 清理
  │                                  │
  │─ POST /api/start-simulation      │
  │   → simulation.start_simulation()│
  │       → db.add_simulation() ────→ INSERT INTO simulation_info
  │                                  │  返回 simulation_id
  │       → 启动仿真线程              │
  │           → 每秒循环:             │
  │               db.add_simulation_data() → INSERT INTO simulation_data
  │                                  │
  │─ POST /api/end-simulation        │
  │   → db.get_current_simulation() → SELECT WHERE status=0
  │   → simulation.stop_simulation()│
  │       → db.end_simulation() ────→ UPDATE status=1
  │   → db.get_simulation_data() ──→ SELECT ORDER BY time_step
  │                                  │  返回历史数据
```

### 10.2 数据格式转换

前后端之间数据格式经历的转换：

```
Python 列表 [3, 2, 5, 1]
    │  ",".join(map(str, ...))  ← 存入数据库前
    ▼
SQLite TEXT "3,2,5,1"
    │  split(",") + map(int, ...) ← 取出数据库后
    ▼
Python 列表 [3, 2, 5, 1]
    │  jsonify(...) ← API 返回时
    ▼
JSON 数组 [3, 2, 5, 1]
```

## 12. 我们遇到了哪些坑，怎么解决的

### 12.1 结束仿真后查不到数据（查询竞争）
**症状**：调用结束 API 时报"无运行中的仿真"。
**原因**：先 `end_simulation()`（status 变为 1），再 `get_current_simulation()`（只查 status=0）。
**解决**：调整顺序，先查信息再停止，并添加 `get_simulation_info_by_session()` 作为兜底查询（不限 status）。

### 12.2 数据库被锁（多线程并发）
**症状**：高并发时偶尔出现 `database is locked`。
**原因**：SQLite 默认模式读写互斥，多个线程同时操作会冲突。
**解决**：启用 WAL 模式 + `check_same_thread=False` + `timeout=30`。

### 12.3 数据精度丢失（打饭速率）
**症状**：数据库记录的窗口人数只增不减。
**原因**：`round(1/5) = 0`，每秒处理 0 人。
**解决**：后端改用浮点累加器（详见 `后端教学文档.md` 问题 12.3）。数据库只负责存储，不负责计算。

### 12.4 window_people 的 CSV 格式设计
**挑战**：SQLite 不支持数组类型，如何存储"各窗口排队人数"这个列表？
**方案对比**：
- ❌ 每个窗口一行：表结构复杂，查询慢
- ❌ JSON 格式：SQLite 无法直接解析
- ✅ **逗号分隔字符串**：简单、直观、存储紧凑。读取时 `split(",")` 还原

### 12.5 数据清理的性能问题
**问题**：每次启动都清理旧数据，启动变慢。
**解决**：概率性触发（~10%）。只要有人用，数据就会定期被清。而且清理时先删子表再删主表，避免外键问题。

## 13. 老师可能会问的问题（Q&A）

### Q1：为什么选 SQLite 而不是 MySQL？
**A**：SQLite 是嵌入式数据库，零配置、零维护，一个文件就是整个数据库。MySQL 需要安装服务端、配置用户权限、管理进程。对于教学演示项目，SQLite 足够，而且携带方便——把 `database.db` 拷走就是完整备份。如果用 MySQL，评审老师需要先装 MySQL 才能运行，增加不必要的复杂度。

### Q2：两张表的关系是什么？为什么这样分？
**A**：`simulation_info` 存仿真的"元信息"（参数、起止时间、状态），`simulation_data` 存"运行时数据"（每秒快照）。这是一对多关系：一次仿真对应多条数据。分表的原因：(1) 避免冗余，参数不用每秒重复存；(2) 查询效率，查参数时不用扫大数据表；(3) 符合数据库设计规范（第三范式）。

### Q3：session_id 是什么？为什么不用 id 做主键？
**A**：`session_id` 是前端生成的 UUID（如 `a1b2c3d4-...`），用于前后端统一标识一次仿真。`id` 是数据库自增主键，用于表关联。两者的分工：`session_id` 是业务标识（外部使用），`id` 是技术标识（内部关联）。要两个是因为同一个 session 可能多次启动仿真（旧记录被清理，新记录有新的 id）。

### Q4：status 字段为什么要用 0/1 而不是文字？
**A**：(1) 整数比较比字符串比较快；(2) 占用存储小（1 字节 vs N 字节）；(3) 不容易因为拼写错误（如 "运行中" vs "运行中 " 多一个空格）导致 bug；(4) 可以方便地用 `status=0` 做条件查询。

### Q5：window_people 为什么要存成逗号分隔字符串，有没有更好的方案？
**A**：更好的方案确实有——比如存 JSON `"[3,2,5,1]"`，但 SQLite 不内置 JSON 解析函数（3.9+ 版本才有部分支持）。逗号分隔的好处是：(1) 简单直观；(2) Python 内置 `split()`/`join()` 足够；(3) 存储紧凑。如果窗口数固定且很多，更好的做法是给每个窗口单独一列，但我们的窗口数通常是 4-8 个，不固定，所以用分隔字符串。

### Q6：WAL 模式是什么？为什么需要它？
**A**：WAL（Write-Ahead Logging）= 预写日志。默认模式下 SQLite 的读和写互相阻塞，写的时候不能读。WAL 模式把写操作先记到独立的 WAL 文件，不影响读操作。这样仿真线程每秒写数据时，API 请求可以同时读数据，互不等待。在 `高频率写 + 随机读` 的场景下，WAL 模式是标准配置。

### Q7：数据是怎么保证不丢失的？
**A**：(1) 数据库层面：每次操作后立即 `conn.commit()` 确保持久化；(2) `try/except + rollback` 确保异常时回滚；(3) 仿真线程的 `finally` 块确保即使崩溃也会记录日志；(4) 多线程层面：停止仿真时有三重兜底——先查 `simulation_ids` 字典、再查 `get_simulation_info_by_session`、最后才返回失败。但也有限制：SQLite 是单文件数据库，没有主从复制，不能防止磁盘损坏。

### Q8：为什么需要清理旧数据？
**A**：仿真每秒产生一条数据记录。如果持续运行，数据库文件会越来越大：(1) 磁盘占用增加；(2) 查询变慢（全表扫描需要更多时间）；(3) SQLite 单文件有大小上限（理论 140TB，但实际超过几 GB 性能就明显下降）。设置 7 天保留期是平衡：够用于回顾最近的仿真结果，又不会无限膨胀。

### Q9：概率性清理（10%）是什么思路？
**A**：`cleanup_old_data` 不是每次启动都执行，而是 `random.random() > 0.1` → 约 90% 概率直接跳过。为什么不每次都清？(1) 大多数时候不需要清（比如昨天刚清过）；(2) 每次启动都做全表扫描影响启动速度；(3) 概率性策略在频繁重启（如调试时）也能保证定期触发，避免了定时任务的复杂性。这是一种"懒清理"策略。

### Q10：数据库测试为什么要用单独的数据库文件？
**A**：(1) 测试会频繁增删数据，不能污染正式数据；(2) 测试之间需要数据隔离（`setUp` 清空表），如果用同一个文件会互相干扰；(3) `tearDownClass` 直接删文件，干净利落。具体做法：先改 `config.DB_PATH = "test_database.db"`，再 `from database import db`，确保 `db` 实例连的是测试库。

### Q11：如果数据库文件损坏了怎么办？
**A**：(1) 预防：每次 commit 确保数据写入磁盘；(2) 检测：可以用 `PRAGMA integrity_check` 检查数据库完整性；(3) 恢复：如果有备份，直接拷贝备份文件覆盖即可；(4) SQLite 的 WAL 模式会自动在下次打开时把 WAL 中的未完成事务回滚或提交，保证数据库一致性。

### Q12：你们的数据库设计有几范式？
**A**：基本符合第三范式（3NF）：(1) 第一范式：每个字段都是原子值（`window_people` 存的是字符串，视为整体）；(2) 第二范式：非主键字段完全依赖于主键（`simulation_data` 的字段都依赖于 `id`）；(3) 第三范式：非主键字段不传递依赖（`simulation_data` 通过 `simulation_id` 外键关联 `simulation_info`，而不是把参数再存一遍）。这是一个中规中矩的关系型数据库设计。

### Q13：`check_same_thread=False` 是什么意思？
**A**：SQLite 默认情况下，一个连接对象只能在创建它的线程中使用。如果仿真线程想用 Flask 主线程创建的连接，SQLite 会报错。`check_same_thread=False` 告诉 SQLite："我知道多线程的风险，请允许跨线程使用"。配合 WAL 模式和锁超时，可以安全地在我们的场景中使用。

### Q14：如果要迁移到 PostgreSQL，需要改什么？
**A**：(1) 把 SQLite 特有的语法（如 `INTEGER PRIMARY KEY AUTOINCREMENT`）改成 PostgreSQL 语法（`SERIAL PRIMARY KEY`）；(2) `window_people` 可以改用 PostgreSQL 的 `INTEGER[]` 数组类型，不再需要逗号分隔；(3) 连接配置改成 PostgreSQL 连接字符串；(4) `datetime()` 函数改成 PostgreSQL 的日期函数。最平滑的方式是引入 SQLAlchemy ORM，改配置即可切换数据库。
